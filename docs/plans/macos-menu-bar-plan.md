# Vigilia: step 3 plan, macOS menu bar app (v0.3)

Implementation plan for [step 3 of the execution plan](execution-plan.md#step-3-macos-menu-bar-app-v03), following [`architecture-plan.md`](architecture-plan.md).

## Context

Steps 1–2 (v0.1, v0.2) are on `main`: a Rust daemon and CLI that keep a Mac awake, including with the lid closed, with crash recovery and battery/heat rules. Step 3 of `docs/plans/execution-plan.md` (milestone M6 in `architecture-plan.md`) adds a native menu bar app in `apps/macos`:
- a countdown in the menu bar
- start / extend / hold to end
- settings: battery floor, heat rule, lid-closed default
- recovery warnings

The app is a thin protocol client: it draws and makes protocol calls, and holds no session logic. It is distributed as a download from GitHub Releases, not the Mac App Store.

Decisions:
- **Doorbell:** the daemon posts a Darwin notification on every session change. The app connects only while a session exists (or while its menu or settings are open), so the service still exits when idle.
- **The lid-closed default is an app-only preference** (UserDefaults). The CLI and protocol keep their current behaviour.
- **Distribution:** a `.dmg` attached to the GitHub release. It is ad-hoc signed by default. Developer ID signing and notarization run only when the CI secrets exist.

Gaps found in the current code that this step has to fill:
- The protocol has no `config.get` / `config.set`.
- The heat rule can't be configured: `crates/core/src/rules.rs` always ends the session at critical heat.
- `vigilia install` writes `current_exe()` into the LaunchAgent plists (`crates/cli/src/lib.rs:121`). It also installs the sudoers rule with plain `sudo`, which needs a TTY (`crates/daemon/src/install.rs:105-124`). A GUI app can't drive it as it is.
- `release.yml` publishes to crates.io only: no macOS artifacts.

## Part A: Rust changes (all additive; protocol stays v1)

**Protocol (`crates/protocol`)**
- `request.rs`: add `Call::ConfigGet {}` (`config.get`, scope `session.read`) and `Call::ConfigSet(ConfigSetParams)` (`config.set`, scope `config.write`).
  - `ConfigSetParams { rules: Option<RulesPatch { battery_floor_percent: Option<u8>, end_at_critical_heat: Option<bool> }> }`. This is a patch: only the fields sent change.
  - Update `method()`, `required_scope()` and the round-trip test.
- `response.rs`: add `Settings { rules: RuleSettings { battery_floor_percent: u8, end_at_critical_heat: bool } }` and `ConfigResult { config: Settings }`. Add `ConfigResult` to `CallResult`.
- `event.rs`: add `Event::ConfigChanged { config: Settings }` and `EventKind::ConfigChanged`.
- Regenerate `schema/protocol.schema.json`.
- New `schema/examples.jsonl`: one example line for every request, response shape and event. It is generated by a test in `tests/schema.rs` and drift-checked the same way as the schema. The Swift tests decode every line.

**Core (`crates/core`)**
- `config.rs`:
  - `RulesConfig.end_at_critical_heat: bool`, default `true`.
  - `Config::save_rules(path, &RulesConfig)`: edits only the `[rules]` keys with `toml_edit`, which is already in `Cargo.lock`, so it becomes a direct dependency. Comments and unknown keys stay. The file is written atomically (temp file, then rename).
- `rules.rs`: the critical-heat rule respects the flag. Add tests.

**Platform (`crates/platform`)**
- Add `fn announce_session_change(&self) {}` (default no-op) to the `Platform` trait.
  - macOS: `notify_post("com.vigilia.session-changed")`, through an `extern "C"` declaration in a new `macos/notify.rs`. It lives in libSystem, so no new crate is needed.
  - `FakePlatform` counts the calls for tests.
  - Stub: no-op.

**Daemon (`crates/daemon`)**
- `Deps` gains `config_path: Option<PathBuf>`. `lib.rs` passes `paths.config`; tests pass a temp path.
- `service.rs`:
  - `config_get()`.
  - `config_set(p)`: validate (floor 0–100, otherwise `bad_request`), persist with `save_rules`, update the in-memory config, then publish `ConfigChanged`. If there is an active session and a power snapshot, rerun the rules straight away, so raising the floor above the current charge ends the session, as at session start.
  - `publish_session()` also calls `platform.announce_session_change()`.
- `dispatch.rs`: route the two new calls. Add them to `calls()` in the every-method-against-every-scope test.
- `install.rs`: split the sudoers part out so it can run separately:
  - `install_agents(program, paths)`.
  - `write_sudoers(user)` for a process already running as root: write `/etc/sudoers.d/vigilia` with mode 0440 root:wheel after `visudo -cf` validation.
  - `remove_sudoers()`.

**CLI (`crates/cli`)**
- `vigilia config get [--json]` and `vigilia config set <key> <value>`, with keys `rules.battery_floor_percent` and `rules.end_at_critical_heat`.
- `install` / `uninstall` gain `--skip-sudoers`.
- A hidden `vigilia sudoers install|remove --user <name>`. It refuses unless euid is 0. The app runs it through the system admin password dialog.
- `watch.rs`: print `config changed` notices (the match must stay exhaustive).

**Tests:**
- dispatch scope matrix
- `config.set` persists, emits `ConfigChanged`, and keeps comments and unknown keys
- raising the floor mid-session ends the session
- `announce_session_change` count on start, extend and end
- the heat flag turned off doesn't end the session
- CLI binary tests for `config get/set`

**Connection lifecycle (energy):**
- **App launch:** connect once for `hello` and `session.status`, then cache the capabilities.
  - Session active: stay subscribed.
  - No session: disconnect, so the service can still exit after `idle_exit_minutes`.
- **Doorbell fires:** connect and subscribe. The first event is the current session.
- **Session reaches `Ended` and the menu is closed:** disconnect.
- **Menu or Settings opened:** connect while open, for fresh capabilities and settings. Disconnect on close when there is no session.
- **Unexpected drop while a session was active:**
  - Show the warning "Service not running, reconnecting".
  - Retry with backoff. Connecting re-activates the socket-activated service, or the app spawns `Contents/Helpers/vigilia daemon`.
  - Stop retrying after about 2 minutes and then rely on the doorbell.
- **Quitting the app:** only closes the socket. The session continues.

**Drawing (energy):**
- The status title shows `1h 23m`. A non-repeating `Timer` is scheduled for the next instant the label changes (from `Countdown`), with a few seconds of tolerance, so there is at most one redraw per minute.
- Indefinite sessions show the elapsed time the same way.
- While the popover is open, a 1 s timer shows seconds; it is invalidated on close.
- No animation in the status item. App Nap is allowed (no `NSProcessInfo` activity assertions).
- Warning state: the status icon switches to a variant with a badge. Needs-attention shows a "Retry" button that calls `session.stop`.

**Capabilities gate the UI:**
- The lid toggle is shown only when `keep_awake_lid_closed` is set. It is enabled only when `/etc/sudoers.d/vigilia` exists; otherwise it shows "Set up…".
- Battery and heat settings are shown only when `power_events` is set.

## Part C: Packaging, setup and release

**Bundle layout:**
- `Vigilia.app/Contents/MacOS/Vigilia` is the Swift app.
- `Contents/Helpers/vigilia` is the universal Rust binary. It goes in `Helpers` because `MacOS/vigilia` would collide with `MacOS/Vigilia` on the case-insensitive APFS volume.
- `Info.plist`: `LSUIElement = YES`, `LSMinimumSystemVersion = 13.0`, version taken from the workspace.

**`scripts/build-app.sh`:**
1. `cargo build --release` for the `aarch64` and `x86_64` Apple targets, then `lipo`.
2. `swift build -c release --arch arm64 --arch x86_64`.
3. Assemble the bundle.
4. `codesign --options runtime --timestamp`: the helper first, then the app. The identity is `$SIGNING_IDENTITY`, or `-` (ad-hoc) when it isn't set.
5. Make `Vigilia-<ver>.dmg` with `hdiutil` (the app plus an `Applications` symlink).
6. If the notarization secrets are set: `xcrun notarytool submit --wait` and `stapler staple`.

**In-app setup (replaces "an installer that runs `vigilia install`"):** shown on first launch, and from Settings.
- **Location check:**
  - If the app runs from an App Translocation path or outside `/Applications`, it asks the user to drag it into Applications first, because the LaunchAgent stores the helper's absolute path.
  - On every launch it reads `~/Library/LaunchAgents/com.vigilia.service.plist`. If `ProgramArguments[0]` isn't the bundled helper, or doesn't exist (for example the app was moved), it offers "Repair". Repair reruns step 1 below.
- **Setup steps:**
  1. **Background service:** run `Helpers/vigilia install --yes --skip-sudoers`. No admin rights needed. It installs the socket-activated LaunchAgent and the recover-at-login job, both pointing at the helper.
  2. **Lid-closed sessions (optional):** show the sudoers rule, then use `NSAppleScript` `do shell script "<helper> sudoers install --user <NSUserName()>" with administrator privileges`. This is the native password dialog, with arguments quoted through `quoted form of`. The same step can add the `/usr/local/bin/vigilia` symlink so the CLI is on `PATH`.
  3. **Launch at login:** a toggle using `SMAppService.mainApp`.
- **Uninstall:** a Settings button runs `uninstall --yes --skip-sudoers`, then the admin step `sudoers remove` and removes the symlink.

**CI / release:**
- **`ci.yml`:** a new `macos-app` job on `macos-latest`:
  - `cargo build -p vigilia`.
  - `swift build` and `swift test` in `apps/macos`, with `VIGILIA_BIN=target/debug/vigilia` so the integration test runs.
  - `scripts/build-app.sh` ad-hoc, to prove the bundle assembles.
- **`release.yml`:** a new `macos-app` job on `macos-latest` that runs `build-app.sh` and uploads `Vigilia-<ver>.dmg` and a `.sha256` with `gh release upload`. Signing and notarization run only if `MACOS_CERT_P12`, `MACOS_CERT_PASSWORD`, `MACOS_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_TEAM_ID` and `APPLE_APP_PASSWORD` exist. Otherwise the job builds ad-hoc, and the release notes explain how to get past Gatekeeper (System Settings → Privacy & Security → Open Anyway).
- **`.gitignore`:** add `apps/macos/.build/`, `.swiftpm/` and `*.dmg`.

## Verification

- `cargo fmt --check`, `cargo clippy --workspace -D warnings`, and `cargo test --workspace` (schema and examples drift included).
- In `apps/macos`, `swift test`, then again with `VIGILIA_BIN=$PWD/../../target/debug/vigilia swift test`.
- Manual checks (step 3 "Done when"), using `scripts/build-app.sh`, the app copied into `/Applications`, and setup run:
  - **Same session in both:** `vigilia start 10m` in a terminal → the menu bar shows `10m` within a second, via the doorbell. Extend in the app → `vigilia status --watch` updates. `vigilia config set rules.battery_floor_percent 20` → the Settings window updates.
  - **Quitting:** quit the app → `vigilia status` still shows the session.
  - **Service killed:** `kill -9` the daemon → the app shows a warning, then reconnects (the session was ended by journal replay). `vigilia start 5m` → the app shows it again.
  - **No session:** no `vigilia` process 5 minutes after the session ends while the app keeps running (`pgrep vigilia`).
  - **Energy:**
    - Menu closed during a 30-minute session: Activity Monitor Energy Impact ≈ 0. Measure with `sudo powermetrics --samplers tasks --show-process-energy`.
    - At most one redraw per minute, checked with a debug counter logged via `os_log`.
    - Record app + service RSS in `docs/energy.md` and the release notes.
  - **Hold to end:** releasing early does nothing; a full hold ends the session.
  - **Lid toggle:** hidden without the sudoers rule; after setup, a lid-closed session works.
